## 2. GOV-001: approvals not traceable outside the agent's session

| Item | Finding |
|---|---|
| What | Both changes of 2026-10-25 were **explicitly approved** before they ran (evidence above). But the approval exists only in the agent's local session log on the operator's computer: not tamper-evident, not visible to a reviewer, not linked to the Vercel deployment, and the approver's identity is the computer's session, not an authenticated step. The deployments ran with the operator's personal Vercel credentials, so Vercel records them as the operator's own actions |
| Severity | Medium (governance). No unauthorised change happened; the gap is that it could not be proven to a third party |
| Interim measure (in place) | Each approval is copied verbatim with its SHA-256 into the private evidence store and listed in section 1 before the change is reported done |
| Measure (prepared, class A, in review) | `.github/workflows/production-deploy.yml`: the only path to change Production code. Started with the exact commit; checks that it is on `main` with a green CI run; the deploy job waits in the GitHub environment **Production**, whose required reviewer is the operator, so GitHub records **who approved, when, for which run and commit**; its first step **refuses to deploy unless an approval for Production is recorded on this run** (unreadable approvals refuse too); deploys through the Vercel API with a token given only to the two steps that call Vercel; checks Production from outside; **promotes the previous deployment back** if a check fails, and reports success only when Vercel shows Production serving it; writes the record (approval, commit, deployments, checks) in the run summary and as a JSON artifact kept 90 days; a separate job without any secret checks Production after every run, even a cancelled one |
| Operator steps to activate it | Create a Vercel token for deployments and store it as the secret `VERCEL_DEPLOY_TOKEN` of the GitHub environment Production; add the variables `VERCEL_TEAM_ID`, `VERCEL_PROJECT_ID` and `GITHUB_REPOSITORY_ID_FOR_VERCEL` (not secrets) to that environment; create a random monitoring token of at least 32 characters and store it both as the secret `LUXIA_MONITORING_TOKEN` of that environment and as the Vercel Production variable `LUXIA_MONITORING_TOKEN`; in Vercel Production also set `AUTHZ_MODE` to `native` and `CRON_SECRET` (random, at least 32 characters): without them the run refuses to deploy; on that environment, set the operator as **required reviewer**, turn on **prevent self-review** if another approver exists, and limit **deployment branches** to `main`; then review and merge the PR. Check once: a run approved by nobody stops at "no approval is recorded" |
| One release, schema and code | Both Production workflows take the **authorized release** (a tag such as `rc-private-beta-1`, or the full SHA) and the **full SHA** it must be. `scripts/ops/verify-release.sh` accepts them only if the tag resolves to exactly that commit, the commit is on `main`, and its latest CI run on `main` succeeded. A moved tag, another SHA, a commit off `main` or a missing or failed CI run all refuse. The **activation gate** (`production-activation-gate.yml`, operation `activation`) checks out that commit, never `main`'s tip: a merge into `main` after the authorization changes nothing in the operation. It verifies the release again after the approval, applies that commit's migrations only, then requires the database to hold exactly them (`scripts/ops/verify-schema-release.sh`). The **code deploy** (`production-deploy.yml`) refuses to send anything unless Production's applied migrations are exactly the release's. The order is therefore: activation of release R, then deploy of release R. Deploying code older than the schema is refused too: a code rollback goes through the deploy's own promote-back, or after the schema is brought back. **One operation at a time, never queued:** each workflow refuses while another activation, identity operation or deploy is queued, waiting for its approval, or in progress (`scripts/ops/verify-no-other-operation.sh`): in its first job, and again inside its Production job after the approval, which also covers a re-run of that job alone. There is no concurrency group, because a group keeps one pending run that a later dispatch replaces. Of two overlapping operations at least one refuses, and both may. Dispatch the next operation only once the previous run has ended; after a refusal, dispatch a new run rather than re-running the old one. The schema check compares migration **names** and refuses a half-applied one; it does not compare their content, so a migration is never edited once applied |
| After each run | Download the artifact `production-change-record-<run>` and copy it, with its SHA-256, into the private evidence store (`approvals/<date>/`): the artifact expires after 90 days, the evidence store keeps it |

### When a run ends red

| Message | Meaning | What to do |
|---|---|---|
| `no approval is recorded` / `approvals of this run cannot be read` | Nothing was deployed | Check the environment's required reviewer, then start a new run |
| `REFUSED: tag … points to …`, `… is not on main`, `no completed CI run on main`, `… is not success` | Nothing was run or deployed: the release named is not the commit given, or not a verified commit of `main` | Check the tag and the SHA in the authorization; never move a release tag, cut a new one |
| `REFUSED: another Production operation is queued, waiting or in progress` | Nothing was run: the log lists the open runs | Let that run end (approve, reject or cancel it in GitHub), then dispatch again |
| `Production's applied migrations are not the release's` (deploy) or `the database's schema is not the release's` (gate) | The schema and the release differ: the lines above it name the migrations missing or extra. In the gate, the migrations already ran: Production holds them | Deploy: run the activation gate for the same release first. Gate: stop, compare with the release, decide with the change record before any new run |
| `LUXIA_MONITORING_TOKEN is missing or shorter than 32 characters`, `… is not set for Production in the Vercel project`, `environment variables cannot be read` | Nothing was deployed | Set the named secret or variable as in the activation steps, then start a new run |
| `after-checks failed` with `readiness=401` | The deployment does not accept the monitoring token: the GitHub secret and the Vercel variable differ, or the deployment predates readiness. The run then **attempted** a rollback. Production is recovered only on positive evidence: the rollback step ended successfully with the line `rolled back: Production serves <previous>` and the record says `Rollback | success`. The job `confirm` then reports `MANUAL CHECK REQUIRED` **by design** (a deployment was attempted and the run failed): the operator checks in Vercel that Production serves the previous deployment named in the record and that `/login` serves LUXIA, and records that check. Anything else (a `ROLLBACK UNRESOLVED` or `ROLLBACK NOT CONFIRMED` line, or no rollback line at all because the step was interrupted, cancelled or timed out) counts as `ROLLBACK UNRESOLVED` | Check the rollback's outcome first; then make the two values equal and start a new run |
| `after-checks failed` with `readiness=503` and `checks` | The deployment runs, but one of authorization (mode not `native`), database (unreachable, or not the restricted runtime role) or session path is not ready. The run then **attempted** a rollback: check its outcome as above | Check the rollback's outcome first; then fix what the false check names before a new run; `database` or `session` false with the previous deployment healthy points to the new code or a migration |
| `ROLLBACK UNRESOLVED` | A deployment of this run may still exist or be running; Production may change later | In Vercel, list the deployments of the project created by this run (metadata `luxiaRun` = `<run number>.<attempt>`, as in the run's URL and attempt; check every attempt of the run); cancel any that is not finished; promote the previous deployment named in the record; confirm `/login` serves LUXIA |
| `ROLLBACK NOT CONFIRMED` | The previous deployment was requested back but Production does not serve it | Promote it in the Vercel dashboard, then confirm `/login` serves LUXIA |
| `MANUAL CHECK REQUIRED` (job `confirm`) | The deploy job did not succeed, or Production failed the public check after the run (also when the deploy job was cancelled or cut off) | Find which deployment serves Production in Vercel and compare it with the record; act as for `ROLLBACK UNRESOLVED` |
| Rule once active | Agents never deploy or promote from a command line again. A promotion for an emergency rollback is also run from a reviewed workflow, or by the operator in the Vercel dashboard |
| What an approval proves | It identifies a GitHub account. Separating people from automation is tracked privately |
| Residual | The operator's own Vercel credentials can still deploy from any computer (cause of the 2026-10-24 incident). External monitoring is what catches that (G6) |
